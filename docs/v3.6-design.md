# Deqi v3.6 — "Smart Harness" Design

**Tag**: v3.6.0 on `desktop-v2` branch
**Goal**: turn Deqi from "lots of tools" into "smarter use of tools". Each item below targets a different surface of the harness loop, not a new tool.

## Why this version, not more tools

v3.1–v3.5 added 7 new tools. Anthropic's "Building effective agents" 2025 update
makes the same observation: the next 10x comes from better use of existing tools,
not from more tools. The four highest-leverage surfaces in our current loop are:

1. **Specialists are stubs** — v3.3's `runSpecialist` returns deterministic text.
   The orchestrator is currently a wrapper around a no-op. v3.6 makes it real.
2. **Context grows unbounded** — `compact()` exists in agent.ts but is never
   called automatically. v3.6 wires it in.
3. **Re-reads everything** — `read`/`webFetch`/`browser.navigate` re-execute on
   the same input. v3.6 adds a small cache.
4. **Plans are static** — `plan.record` writes a JSON file. Nothing reflects
   progress back to the model. v3.6 surfaces "you are on step N of M" so the
   model doesn't drift.

## v3.6 deliverables

### 1. Real LLM-backed specialists (`runSpecialist` is now async + LLM-backed)

**Before (v3.3)**: `runSpecialist(name, task, sandbox): string` returns a
deterministic stub. The orchestrator tool's real value is zero.

**After (v3.6)**: `runSpecialist(spec, task, sandbox, ctx): Promise<string>` creates
a real `Agent` (via the same pattern as the `subagent` tool), gives it the
specialist's frozen system prompt + read-only tool subset, runs it for ≤12 turns,
and returns the final assistant text.

**Harness contract**: the server passes `harness.orchestrator = { registry, parentTools, defaultModelId }`.
The orchestrator tool reads it from `ctx.harness?.orchestrator`. When it's missing
(in standalone tool tests, or in `runSpecialist` called without a harness),
`runSpecialist` falls back to a deterministic stub so the existing v3.3 test
suite still passes.

**Failure mode**: if the LLM call fails (no provider, timeout, model error), the
orchestrator tool returns the error to the parent as a normal `isError: true`
result. The parent's session is not corrupted.

### 2. Auto-context-compaction in `Agent.run()`

**Before (v3.0–v3.5)**: `compact()` exists but is never called. Long sessions
hit the model's context limit and either truncate the prompt or error out.

**After (v3.6)**: after each turn, the agent checks `isContextNearLimit()`. If
`used / contextWindow >= 0.85`, it calls `compact()` before the next turn. The
compaction emits a `context_compacted` event with the tokens-before / tokens-after
counts, so the UI can show "I forgot 2,400 tokens of context".

**Safeguard**: don't compact on the first turn (would be a no-op), and don't
compact twice in a row (in case compaction itself blows up the context).

### 3. Tool result cache (LRU + TTL + mtime-aware for `read`)

**Before**: `read` re-reads the file every time. `webFetch` re-fetches the URL.
`browser.navigate` re-downloads. A long session that consults the same file or
URL 10 times pays the IO/network 10 times.

**After (v3.6)**: a small LRU+TTL cache sits between the tool and the executor.
- `read`: cache key = (path, mtime-ms). File mtime is checked via `fs.statSync`.
  Changed mtime → invalid. 5-min TTL safety.
- `webFetch`, `browser.navigate`: cache key = URL. 5-min TTL. Configurable via
  the tool's `cacheTtlMs` parameter (default 300_000).
- Other tools: pass through. (We don't cache `bash` or `write` — side effects.)

**Implementation**: `cache.ts` (LRU + TTL) + a `withCache(tool, opts)` wrapper
that the agent applies at execution time. The cache is per-session (not global)
to avoid stale data across projects.

**Limits**: 256 entries, 16MB total content. Eviction by LRU.

### 4. Plan enforcement (progress reflects to the model)

**Before**: `plan` writes a JSON file. After `plan.record`, the model has to
remember which step it's on. It forgets, drifts, and re-does steps.

**After (v3.6)**: when a tool call comes in, the agent checks the active plan
and updates step status:
- if the tool name matches a step's `tool` field, mark that step `in_progress`
- if the next 1-2 tool calls succeed and touch the step's `target`, mark `done`
- if a tool fails and was for a step, mark `blocked`

The system prompt gets a small "Plan progress" block injected on each turn:
```
## Plan progress (3 of 5 done)
- [DONE]      read AGENTS.md
- [DONE]      plan 3-step migration
- [IN-PROGRESS] write migration.ts       ← you are here
- [ ]          write tests for migration
- [ ]          run test suite
```

This is the same pattern Anthropic describes in "Plan-then-execute" patterns:
the plan is a contract the model can look at to know what to do next.

## Non-goals (deferred to v3.6.1+)

- Real headless browser (Puppeteer/Playwright) for `browser.screenshot` — too heavy
- MCP HTTP+SSE transport — defer
- File watcher for live re-cache — defer
- Cross-session pattern detection (embeddings) — defer
- Streaming sub-agent events to the UI — defer to v3.7

## Test plan

Two new test suites in `examples/smoke/`:

### `v3.6-harness-test.ts` (~40 asserts)
- `runSpecialist` is now async; with no orchestrator ctx, returns a stub
- `runSpecialist` with a real ModelRegistry stub returns a real report shape
- `compact()` is called when context exceeds threshold (spy on the Agent)
- `compact()` is NOT called on the first turn
- `compact()` is NOT called twice in a row if it just ran
- LRU cache: hit, miss, eviction, TTL expiry, mtime-invalidation for `read`
- Plan enforcement: `plan.record` then a matching tool call updates the step
- Plan progress injection shows up in the system prompt

### `v3.6-tool-cache-test.ts` (~25 asserts)
- `read` cache: same path + same mtime → cache hit, no second fs.readFileSync
- `read` cache: changed mtime → cache miss, re-read
- `read` cache: TTL expiry → cache miss
- `webFetch` cache: same URL within TTL → cache hit
- `webFetch` cache: same URL after TTL → cache miss
- LRU eviction: 257th entry evicts the oldest
- Cache is per-session (no cross-project leakage)
